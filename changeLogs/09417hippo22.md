Security fixes (verified applied, focused suites green):
- #4286 — Safe signing is now bound to what the user approved. Every signing
  completion event on the UI bus carries a fingerprint of the exact request
  (approval id, origin, account, payload hash) and each waiting screen only
  consumes events matching its own operation, closing the cross-window and
  cross-request signature-result confusion class. Separately, every step of
  the Safe confirmation flow (typed-data generation, add-confirmation,
  add-signature, post) now re-validates the reviewed proposal against the
  transaction hash shown at review time — a proposal replaced after approval
  fails closed with "The Safe proposal changed. Please review it again."
  instead of signing the new bytes; the approval id, component, nonce, chain
  and the recomputed EIP-712 hash are all re-checked at the background edge,
  and the previously reachable silent-sign branch now throws.
  `operation` values are normalized fail-closed. Regressors:
  gnosisSafeTx, gnosisSigningBinding, gnosisTransactionBuildBinding,
  gnosisOperation, signEvent tests.
- #4290 — the typed-data review screen is bound to the request it shows:
  legacy V1 vs V4 detection is normalized, a payload that fails to parse can
  no longer render a review with content (the security check treats it as
  failed rather than falling open), and the chain used for policy display
  comes from the signed payload's domain (or this approval's captured chain
  for domainless payloads) instead of re-reading whichever site chain is
  live when the component renders. Regressor: signTypedDataSecurity.
- #4296 — `personal_sign` bytes the user reviews are now byte-identical to
  the bytes handed to the signer (shared normalizeSignText, including
  odd-length hex padding). Adding a custom network from an approval is bound
  to that approval: account, dApp-site, chain and unlock state are re-checked
  immediately before the persistent write, and a cancelled/locked/stale
  approval revokes instead of committing a chain the user did not confirm.
  Regressors: signText, networkApproval tests.
- #4297 — cancelled and superseded transactions stop before signing and
  before broadcast: the signing transaction is resolved up-front and every
  keyring sign, EIP-7702 authorization sign, broadcast and retry-fallback
  step re-checks that the exact approved request is still active and the
  wallet still unlocked (fail-closed throw where the check had previously
  been commented out). Legacy V1 typed-data fields are preserved through the
  review highlighter so nothing shown differs from what is signed.
  Regressors: blockedAddressSigning, dappTransactionBinding,
  customNetworkEip1559Signing, tempoSigning tests.
- #4276 — the "Retry" target in waiting popups can no longer be hijacked by
  unrelated dApp requests (a polling `eth_chainId`/`eth_accounts` used to
  replace the retry function and replay the poll instead of the signature,
  and an old target could replay an already-approved request): only requests
  that hand off to a waiting component register a target, and it is cleared
  when that waiting approval ends. A Safe-owner signing attempt that fails
  reports failure to the popup it belongs to only, never to whichever
  approval is on screen now. Regressors: rpcFlowRetryTarget,
  approvalSigning, rpcFlowApprovalGuards tests.
- #4295 — removing an address that a dApp had selected now disconnects that
  site (cleared account, connected site removed) instead of silently
  re-pointing the site at whichever account the wallet has current: a dApp
  can no longer keep a session bound to a removed address's successor.
  Regressor: removeAddressPrivacy test. The accompanying remote-asset
  privacy work in that PR targets the removed live-widget surface.
